## المعمارية النهائية
```
[Public Site — static vanilla, نفس المستودع]
   │  fetch محتوى من /api/content مع fallback للنص الثابت (الموقع يعمل حتى لو الـ API سقط)
   │  analytics beacon → /api/track
   │  contact form → /api/contact
[Supabase]  Postgres + RLS │ Auth (admin واحد) │ Storage (وسائط + CV)
[Admin Dashboard — React+Vite SPA، مجلد dashboard/ منفصل، نشر Vercel مستقل، noindex]
   │  Supabase JS client مباشرة (RLS يفرض التخويل خلفياً)
[Vercel Serverless — api/* داخل موقع العام: contact, track, content, cv-download]
```
- المفتاح العام لـ Supabase (anon key) فقط في الواجهات — الكتابة الإدارية محمية بـ RLS عبر auth وليس عبر الواجهة.
- Dashboard على مسار/نطاق منفصل + `noindex` + robots Disallow + مصادقة Supabase Email/Password (مستخدم واحد).

## نموذج البيانات (Supabase Postgres)
`site_settings`, `about_profile`, `projects` (+ status: draft/published/archived, is_featured, sort_order, case_study jsonb, soft delete deleted_at), `skills` (+category, enabled), `certifications`, `experiences` (+kind: work/internship/independent/academic/volunteer), `recommendations`, `social_links`, `cv_versions` (+is_active, download_count), `contact_messages` (+status: new/in_review/replied/archived, starred, notes), `anonymous_visitors`, `visitor_sessions`, `analytics_events`, `page_views`, `audit_logs`, `admin_users` (يُدار عبر Supabase Auth).
- RLS: قراءة عامة فقط للصفوف المنشورة؛ كل الكتابة تتطلب مستخدم admin مصادقاً؛ analytics ingest عبر service role داخل serverless فقط.
- Indexes على: slug, status, created_at, event_type, session_id.
- SQL migrations كملفات في `supabase/migrations/` + بيانات أولية seeded من المحتوى الحالي الحقيقي (لا اختراع أي بيانات).

## مراحل التنفيذ (بوابة بعد كل مرحلة + git commit)
- **M0 — الحماية**: git init + commit كامل للحالة الحالية + branch develop. (نقطة الاسترجاع)
- **M1 — البنية التحتية**: إعداد Supabase (تحتاج منك إنشاء مشروع مجاني وتزويدي بـ URL + anon key + service_role في .env)، Schema + RLS policies + seed المحتوى الحالي، إعداد repo بنية monorepo بسيطة: `/` (الموقع) + `/admin` (Vite React).
- **M2 — طبقة API**: api/contact.js (تحقق server-side + rate limit + honeypot + حفظ في Supabase)، api/track.js (استيعاب أحداث)، api/content.js (قراءة منشور)، api/cv-download.js (تتبع + proxy من Storage)، أسرار فقط server-side.
- **M3 — الموقع العام V2**: هرمية المشاريع (Featured dominant + Secondary + Additional)، دراسات حالة معمّقة Problem→Approach→Implementation→Result بكشف تدريجي، Hero محسّن (من أنت/ماذا تبني/CTA واضح/CV)، مهارات مصنّفة، شهادات وخبرات وتوصيات مدعومة ببيانات، ربط النموذج بالـ API مع حالات نجاح/فشل، تتبع أحداث كامل، تحسين SEO (canonical, og, JSON-LD محدث، sitemap) — مع الحفاظ على كل ما يعمل (i18n/RTL، 5 ثيمات، PWA، a11y).
- **M4 — Admin Dashboard**: React+Vite: تسجيل دخول، نظرة عامة بإحصائيات ورسوم، CRUD كامل (projects/skills/certifications/experiences/recommendations/about/settings)، Draft→Preview→Publish، Soft delete→Restore→حذف نهائي مؤكد، إدارة وسائط (رفع آمن + تحقق نوع/حجم)، إدارة CV (إصدارات + active + تتبع تحميلات)، Inbox رسائل (new/in_review/replied/archived + بحث + نجوم + ملاحظات)، Analytics views (Overview/Traffic/Pages/Projects/Conversions/Audience/Live)، Audit Log، Site Settings + feature flags.
- **M5 — الأمان P0**: مراجعة RLS على كل جدول، rate limiting، تحقق رفع الملفات server-side (نوع/حجم/اسم آمن)، لا أسرار في العميل، protected routes، audit شامل، اختبار محاولات وصول غير مصرح.
- **M6 — الأداء/SEO/وصولية**: Lighthouse، الضغط، lazy loading، noindex للداشبورد، robots/sitemap، فحص a11y وRTL وreduced motion.
- **M7 — الاختبارات والتحقق**: node --check، اختبارات unit للتحقق والتحليلات، E2E بالمتصفح (Playwright) للمسارات الحرجة (عام: تنقل/مشروع/CV/تواصل/لغة، Admin: دخول/CRUD/publish/restore/رفع CV)، تحقق متصفح حقيقي ديسكتوب+موبايل+لوحة مفاتيح فقط.
- **M8 — التقرير النهائي**: النشر (الموقع الحالي + dashboard كمشروع Vercel ثانٍ)، توثيق DEPLOYMENT + MAINTENANCE + تقرير قبل/بعد.
